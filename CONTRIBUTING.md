# Contributing

How to work on LoveLight Presenter: where the rules live, and how code is
written, tested, and committed.

## Sources of truth

- UI appearance, sizes, states, and copy rules: the design system in
  `design/system/project/`. When a draft board disagrees, the design system
  wins. Draft boards are kept outside the repository.
- Behavior and data: `docs/spec/`.
- Stack and dependencies: `docs/TECH.md`. Add a dependency only after you record
  the reason in `docs/decisions.md` and the lead approves it.
- When ProPresenter has the same feature, follow ProPresenter. Don't claim that
  something follows ProPresenter unless you checked.

## Language

- Write documents, code comments, test names, log messages, and commit messages
  in English.
- Keep product UI strings in Korean. Use the glossary in the design system
  README (출력, 슬라이드, 예배 순서, 템플릿, 구성, 이름표, 지우기, 본 화면, 무대
  화면, 방송 자막, 테마, 진행 도구, 퀵 실행).
- Never use middle dots (·) or em dashes (—) anywhere.
- Don't put explanatory sentences in the UI. Show state with shape and color,
  and give reasons in tooltips.

## Style guides

- Documents:
  [Google developer documentation style guide](https://developers.google.com/style).
- Markdown:
  [Google Markdown style guide](https://google.github.io/styleguide/docguide/style.html).
- TypeScript:
  [Google TypeScript style guide](https://google.github.io/styleguide/tsguide.html).
- React and JSX:
  [Airbnb React/JSX style guide](https://github.com/airbnb/javascript/tree/master/react),
  because Google has none.
- CSS and HTML:
  [Google HTML/CSS style guide](https://google.github.io/styleguide/htmlcssguide.html).
- Code review and changes:
  [Google engineering practices](https://google.github.io/eng-practices/). Keep
  changes small and focused, and describe them clearly. Reviewers approve a
  change once it improves the overall health of the code, even if it isn't
  perfect.
- When a guide and Prettier disagree on whitespace, Prettier wins.

## Formatting

- Prettier formats all code, CSS, JSON, and Markdown in the repository. The
  settings in `.prettierrc.json` follow Google's `gts` defaults: 80 columns,
  2-space indentation, single quotes, semicolons, trailing commas, no spaces
  inside braces, no parentheses around a single arrow parameter. Markdown prose
  wraps at 80 columns.
- `.editorconfig` sets UTF-8, LF line endings, a final newline, and trimmed
  trailing whitespace.
- Run `npm run format` before you commit. `npm run format:check` must pass.
- `design/` is excluded because its files are generated by its own scripts.

## Comments

Keep comments to a minimum. Only these three kinds are allowed:

1.  Documentation comments in [TSDoc](https://tsdoc.org) form (`/** ... */`) on
    exported APIs, where the name and type don't say enough. Use TSDoc only, not
    JSDoc: don't repeat types in tags (`@param name - what it is`, not
    `@param {string} name`), because TypeScript already carries them.
2.  `// NOTE(0913vision): ...` in English, for context that the code can't
    express (why something is done a certain way, an outside constraint).
3.  `// TODO(0913vision): ...` in English, for work that must happen later.

Any other comment is not allowed, in TypeScript, CSS, and config files alike.
Don't comment out code; delete it.

## Code

Stability comes before features. Every change must avoid runtime errors, prove
itself with tests, and keep memory and performance flat over hours of use. The
full bar is "Quality bar" in `docs/TECH.md`.

- Know and apply these clean code rules in every change. Reviewers check them
  and request changes when a rule is broken:
  - Use names that say what a thing is or does, so it needs no comment.
  - Keep functions small and make each do one thing at one level of abstraction.
    Prefer few parameters; pass an object when there are more than three.
  - Give each module and class a single responsibility.
  - Don't repeat yourself. Extract shared logic instead of copying it.
  - Replace magic numbers and strings with named constants or tokens.
  - Make side effects explicit. A function that reads state doesn't change it.
  - Keep error handling separate from the main logic, and never swallow an error
    silently: log it or return it as a result.
  - Leave the code you touch cleaner than you found it.
  - Keep tests fast, independent, repeatable, and readable.
- Keep code smells to a minimum. Reviewers flag these and ask for a fix: long
  functions, large classes or modules, long parameter lists, boolean flag
  parameters, duplicated code, deep nesting (prefer early returns), dead or
  commented-out code, speculative generality (code for needs that don't exist
  yet), primitive obsession (use named types for ids, units, and states),
  feature envy (logic that belongs to another module), and changes that force
  edits across many unrelated files.
- Prefer modern language features as long as they don't conflict with the guides
  above: `const` and `let` (never `var`), ES modules, `async` and `await` over
  promise chains, optional chaining and `??`, destructuring, `for...of`,
  template literals, `readonly`, `satisfies`, string literal unions,
  `Array.prototype.at`, `structuredClone`, and `Object.hasOwn`. Where the Google
  TypeScript guide decides otherwise, it wins (for example, use TypeScript
  `private` instead of `#private` fields).
- Use TypeScript strict mode. Don't use `any`, type assertions that bypass
  checks, or the non-null assertion `!`. Make every `switch` exhaustive.
- Validate every value from outside the process (files, IPC messages, the
  clipboard, media metadata) with a schema before you use it.
- The main process owns the live output state. Windows hold copies only and
  change it by sending commands to the main process.
- Write files atomically: write a temporary file, flush it, then rename it.
  Preserve unknown fields.
- An exception in the output path (output windows, live state handling) must
  never stop the output. Log it and keep the last good state.
- Every new behavior and every bug fix comes with unit tests. Reviews of changes
  without tests are not approved.
- Release everything you register: event listeners, timers, IPC listeners,
  `URL.createObjectURL` results, video and audio elements, windows. Cap the size
  of every cache and list.
- Output windows run for hours. Create as little as possible per slide (DOM,
  images, video elements) and reuse what you can.
- Re-render only what changed: use state selectors and memoization, and
  virtualize long lists.
- Use design token CSS variables (`var(--bg-panel)`) for every color, size, and
  spacing value in the UI.

## Code structure

The layers and their order are in "Code structure" in `docs/TECH.md`, and lint
(`llp/layer-imports`) enforces them. These rules keep the structure right as it
grows:

- Imports flow one way: a layer uses only the layers below it. When a lower
  layer needs something from a higher one, the thing is in the wrong place; move
  it down instead of reaching up.
- One rule lives in one place. A rule that needs no I/O goes in `src/core/` with
  its tests, and every caller uses it. The previews and the output draw with the
  same rules; never write a second copy for one view.
- A feature owns its code in its folder. 진행, 준비, and 화면 설정 compose
  features in `app/`; they don't own them.
- An IPC call is declared once, in its area's file in `src/contracts/ipc/`, and
  main answers it with the same endpoint.
- A change that moves code changes nothing else. Moves and behavior changes go
  in separate commits.
- `src/` holds no test code. Tests live in `test/`, in the folder that mirrors
  the code they test (`src/core/x.ts` is tested in `test/core/x.test.ts`,
  `src/renderer/src/ui/y.tsx` in `test/renderer/ui/y.test.tsx`). Shared mocks
  and fixtures live in `test/fixtures/` and are imported as `@fixtures/...`.
  Don't test the same behavior twice.

## Tests

Every test is one of two kinds:

- A **unit test** checks one module at its own layer. Everything outside the
  module is a mock: other layers, other modules' state, and outside systems
  (git, the file system, Electron, another process).
- An **integration test** runs several layers together for one user goal, and
  its title names that goal, for example "saves an imported song to the
  library". There are few of them: one per goal, not one per case.

A test that runs the real code of other layers to check one module is neither
kind. Rewrite it as a unit test of that module.

A module is what one public entry point does, together with the private parts
registered into it. The live store and its slices are one module, tested through
the store; a slice is not tested alone.

### Folders

| Folder                                                                      | Holds                                                                                                                                                                                 |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `test/core`, `test/contracts`, `test/main`, `test/preload`, `test/renderer` | Unit tests, at the path of the module under `src/` (`test/renderer` mirrors `src/renderer/src`)                                                                                       |
| `test/integration`                                                          | Integration tests that run in the test process: `.test.ts` in Node, `.test.tsx` in jsdom                                                                                              |
| `test/ui`                                                                   | Integration tests that start the real app                                                                                                                                             |
| `test/fixtures`                                                             | Shared mocks and sample data. Area folders mirror `src/`; files at its root are generic helpers (temporary folders, the mock clock, git repositories, process trees, Electron launch) |
| `test/setup`                                                                | Vitest setup files                                                                                                                                                                    |

`src/` holds no tests, mocks, or sample data for tests.

### Rules

- Name every test double a mock (`mockLlpApi`, `installMockClock`), never a
  fake.
- `test/ui` holds wiring checks only: the app starts and quits, a window opens,
  a file survives save and restart, an edit in a focused field is saved on
  close, crash recovery. Feature behavior goes in unit tests. How a screen looks
  is checked by eye against its draft, not by measuring a real window.
- Fix a flaky test by removing its race, not by waiting longer. A longer wait
  needs measured times in a `NOTE(0913vision)`.
- Each test sets up what it needs and cleans up after itself. It never depends
  on another test or on what one left behind.
- Test behavior that can break. Code without logic (wiring, constants, types,
  re-exports, one-line adapters that the types already check) is not a test
  target.
- Test each behavior once, where it is owned. Don't repeat a parser's cases in
  every caller.

## UI consistency

The user judges the app by using it, so these hold across every screen:

- One kind of control looks and behaves the same everywhere: every menu has the
  same indent, highlight, keyboard, and disabled rules; every list row and every
  dialog likewise. Fix a rule in the shared component, never in one screen.
- Every action shows its result at once: no wait without feedback, no silent
  save, no item that vanishes and comes back while it updates.
- The target of a right-click or a keyboard action is visibly marked while the
  menu or action is on it.
- A control sits next to what it acts on, and each workspace looks like itself,
  so the user always knows where they are.
- Names are the words the user uses, from the glossary. Don't invent names or
  translate English UI terms; ask when no word fits.
- Follow the draft. Compare every UI change with its draft board and the design
  system by eye, with screenshots, before it merges. A copied ProPresenter
  layout or shortcut that doesn't fit Windows or this app isn't a reason.

## Commit messages

- Write one line only:
  `tag(scope): <one English sentence starting with a base-form verb>`.
- Use one of these tags:
  - `break`: breaks existing behavior, a file format, or a shared contract.
  - `feat`: adds a feature or changes behavior.
  - `fix`: fixes a bug. Kept apart from `feat` so that every fix that goes into
    a release before a service is easy to find.
  - `refactor`: changes structure without changing behavior, including
    performance work.
  - `style`: changes appearance without changing behavior (formatting, names,
    matching UI values to the design system).
  - `docs`: changes documents only.
  - `test`: adds or changes tests only, with no change to the code they test.
  - `chore`: changes configuration, dependencies, build, CI, or test tooling.
- The scope is the area you changed, for example `live`, `shell`, `ui`, `store`,
  `prep`, `output`, `design`, or `repo`.
- Don't add a body, a blank line, `Co-Authored-By`, or any other trailer, even
  when a tool adds one by default.
- The one exception is the version bot on GitHub, whose commits read
  `Bump version: x.y.z`. Never write that message yourself.
- Examples: `feat(live): add undo for the last clear`,
  `fix(shell): keep the output dot visible on hover`,
  `docs(spec): describe the service file format`.

## Public repository

The GitHub repository (0913vision/llpresenter) is public. Never commit secrets,
personal data, or copyrighted lyrics. Use public-domain text or invented
sentences for sample lyrics. Never commit machine-specific details either: local
paths, user names, ports, or temp folders. Tests use neutral paths such as
`C:\data`.

## Checks

- GitHub's Windows runners check every pushed branch: type check, lint, format
  check, build, and unit tests. Nothing is checked on this computer. A branch
  that changes only Markdown documents gets the format check only. A review
  request needs a green run of its head commit.
- A push to `main` bumps the version and, beside it, measures test coverage. The
  coverage run records the number and never fails on it. The target is 80% of
  lines; the lead and the user decide from that number when to improve coverage.
  Writing good tests with every change stays the rule.
- The single steps are `npm run typecheck`, `npm test`, `npm run format:check`,
  and `npm run build`.
- Passing checks prove the code, not the product. A UI change is done only when
  someone has used it in the real app and compared it by eye with its draft: the
  place it appears, what each click does, and how it fits the screens around it.
  A script that checks spec rows is not that check.
