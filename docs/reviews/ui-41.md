## What changed and why

The 다른 항목 group of 항목 추가 has 성경 구절. Choosing it turns the popover's
search field into a reference field (placeholder `성경 구절`) and keeps the
popover open. Each input goes through `window.llp.bible.lookup` (offline, with
the default translation) and the popover lists:

- the typed passage when it is valid, with its normalized name and `절 N개`;
- the books the text could still become, each with its resolved range and verse
  count (only books that resolve).

Enter or a click inserts a Bible passage item with the default settings
(translation, normalized reference, `split: verse`, `reference: every`,
`verseNumbers` from the 환경설정 option, no translation name), at the end of the
selected item's group like other items. If the selected row is a 빈 자리 that
accepts Bible passages, the passage fills it, keeping the slot's id and unknown
fields (spec 05).

- The default translation is the one marked `default` in `bible.json`; the verse
  number option comes from the preferences, both read once when the field opens.
  An answer for an older input is dropped.
- `Menu` items take `keepsOpen`, for items that switch a menu to another mode;
  the menu stays open and focus returns to the search field (Menu README).
- `ServiceOrderEdits.fillSlotWithPassage()` fills a Bible slot in place as one
  undo step and refuses other slots (`invalid`).

## Team member's reply

Round 1 (codex3, Request changes), answered in one new commit:

1.  The lookup state is per opening. Closing the popover clears the default
    translation and the reply, and a reply counts only when its input and its
    translation match what is shown, so a reopen after a change of the default
    translation never shows or inserts an old answer. Test: a lookup is left
    unanswered, the popover closes, the default translation changes, the popover
    reopens, and the old answer arrives; it is not shown, and the inserted
    passage has the new translation.
2.  Lookups run one at a time and only the newest input waits
    (`latestRunner.ts`), so the main process never sees more than one request
    from the popover, and the last input runs when the slow one returns, also
    after a failure. Tests: the runner (newest waiting task wins, runs after a
    failure) and the popover (typing during a slow first lookup asks once for
    the final input and shows its result).
