## What changed and why

A 빈 자리 that accepts songs becomes a song item when a 라이브러리 song is
dropped on it, or when a song is chosen in quick add while the slot is selected
(spec 05: "Dropping on a song slot fills the slot", "Dropping or inserting an
item of that kind on a slot fills it, and it becomes a normal item"). The new
song item has the default 구성, no background override, and no start 매크로,
takes the slot's place and keeps its id; Ctrl Z restores the slot.

- **Contract (additive).** Slot rows of the 진행 projection carry an optional
  `accepts` (`song`, `bible`, or `slides`), the slot's own `slot` field, which
  the main process builds from the item (`showService.ts` in `src/main/store/`
  and the row schema in `src/shared/schema/showService.ts`). `slotKinds` is now
  exported from the service schema. A row without it is still valid; an unknown
  kind is refused; other kinds of row don't carry it. I named the field
  `accepts` instead of `slot` because the row's `kind` is already `slot`.
- **Edit.** `ServiceOrderEdits.fillSlotWithSong()` replaces the slot in place as
  one undo step. It refuses a slot of another kind (`invalid`), an item that
  isn't a slot or is gone, and a song that no longer exists, all without an
  edit.
- **Drag.** `useServiceOrderDrag` takes `onFill`: over a song slot, a library
  song drag shows no insertion line and a drop fills the slot; anywhere else it
  inserts as before.
- **Slot rows** show the icon of the kind they accept: `song`, `book`, or
  `slides`.

## Team member's reply

Round 1 (codex5, Request changes), answered in one new commit:

1.  The filled slot keeps its id: the song item that replaces it has the slot's
    own id, so a selection on the slot stays selected after the push, and the
    center panel shows the song. The earlier decision "the slot keeps no id" is
    withdrawn. Tests: a selected slot is filled by a drop and the projection
    update keeps `openItemId` and shows the song row selected; the quick add
    test checks the same id; the edit test checks the item is
    `{id: slotId, song}`.
2.  The missing-song case now targets an unfilled song slot and answers
    `not-found` without an edit (the nit); the Bible slot keeps its own
    `invalid` case.

Round 2 (codex2, Request changes), answered in one new commit: filling a slot
keeps the slot's unknown fields. Only `slot` and `title` are removed; the id and
every other field stay, and `song` is added, so the song defaults hold (no
`arrangement`, `background`, `macro`, or `memo`). Test: a slot with
`future: {keep: true}` is filled and the item is `{id, song, future}`; undo
brings back the exact slot. It fails on the round 2 code, which rebuilt the item
as `{id, song}`.
