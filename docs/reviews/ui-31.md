## What changed and why

P3a shows the selected 예배 순서 item in 준비 and edits it. This request adds
the model that the panels in the next requests read and call; it adds no UI.

1.  **One item update.** `state/serviceItemUpdate.ts` changes one item's own
    fields against the service's fresh revision and keeps every other item and
    unknown field. `updateServiceBackground` already did this for the background
    override, so it now delegates to the helper instead of copying it; the 구성,
    start 매크로, and memo of later requests use the same helper. Its existing
    tests pass unchanged.
2.  **One writer per song.** The item's chip strip changes the order of the
    chosen 구성 in the song file (spec 05: chip edits show in every 예배 순서
    that uses that 구성). The song editor store already keeps one `SongSession`
    per song, which coalesces saves, serializes writes, and handles stale and
    failed writes. `SongEditorStore.attach()` now gives an item the song's
    session without opening it in the editor, and `sessionOf()` finds it, so the
    window never has two writers for one song. Session creation moved from
    `open()` into a private `sessionFor()` that both use.
3.  **Order edits as undo steps.** `SongSession.setArrangementSlides()` (and
    `SongHistory.setArrangementSlides()`) replace a named 구성's order as one
    undo step and save it like any other song change. They refuse 기본, a
    missing 구성, an unchanged order, numbers outside the song's 슬라이드, and
    read-only songs.
4.  **The item store.** `prep/service/ServiceItemStore` shows one item
    (`show({serviceId, itemId})`): it reads the service, follows newer pushes of
    that service only, drops a read that answers after another service was
    chosen, and, for a song item, attaches the song's session (reusing one the
    editor already holds). `chooseArrangement()` sets or removes the item's
    `arrangement`; `setOrder()` changes the chosen 구성's order through the
    session. One item edit runs at a time. Refusals and failed reads show a
    notification, with 다시 불러오기 for reads; `write-failed` keeps the applied
    edit and reports that the file wasn't saved.

## Decisions I made (for the lead to confirm)

- Chip edits use the song's `SongSession` instead of a separate `song.update`
  writer, so they join the editor's undo history and its save serialization.
  Ctrl Z in the song editor can undo a chip edit.
- An item whose `arrangement` names a 구성 the song no longer has behaves as
  기본: its order can't be edited.
- Size: about 450 code lines and 420 test lines. The UI is the next request.
